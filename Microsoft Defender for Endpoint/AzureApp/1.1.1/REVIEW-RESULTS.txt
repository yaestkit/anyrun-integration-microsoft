Independent review of Azure App 1.1.0 inputs / revised test packages 1.1.1
Date: 2026-10-02

DECISION
The supplied 1.1.0 ZIP files should not be treated as release-ready.
Revised 1.1.1 packages are prepared for controlled Azure acceptance testing in
NEW resource groups. They are NOT certified and were NOT deployed by this review.
The original files under Documents/Claude/MDE were not modified.

CONFIRMED AND FIXED
1. N1: HTTP errors with a non-JSON body lost their HTTP status.
   aiohttp.ContentTypeError inherits ClientError, while requests.JSONDecodeError
   inherits both ValueError and RequestException. The outer exception-chain
   classifier incorrectly turned an already classified HTTP response into an
   unknown transport outcome. An explicit SandboxAPIError handler now preserves
   the status before the generic classifier runs. Reproduced before the fix:
   10 aiohttp cases (GET/POST x 401/403/413/429/502) and one requests 413 case failed.
   All pass after the fix. Real SDK 1.14.19 offline checks also pass for Windows,
   Linux and Base connectors, using real aiohttp/requests exception types.
   This fixes classification; it does not guarantee a proxy never accepted a POST
   before returning an error. Ambiguous outcomes still require manual recovery.

2. Both CreateUiDefinition files used steps('basics').flexRegions for a control
   defined in Basics. Microsoft documents basics('flexRegions') for that scope.
   The original empty-response bypass additionally made validation fail-open.
   Both checks now use basics(), coalesce missing value to an empty array, and
   require the selected region to appear in the response before proceeding.
   This applies to a loading, empty, or API error response as well.
   The unsupported orgDomain/FLEXCONSUMPTION filter was removed: the API request
   already filters by SKU, and the official Azure CLI uses the returned names
   without that additional filter. Selected subscription/resource-type location
   restrictions remain in Basics. Azure portal behavior still needs live testing.

3. Documentation links had been switched to official main despite the user's
   instruction to retain the test fork. Relevant wizard links now point to
   yaestkit/anyrun-integration-microsoft/tree/asyncv2. The runtime packages use
   local artifacts/, not a mutable GitHub code-download URL. No remote was changed.

AGREED WITH THE AUDIT
- Recovery changes F1-F4 and F6 are present in the actual Sandbox artifact.
- Queue retry visibility is 60 seconds; initial Live Response pause is 10 seconds.
- Logic App has bounded submission/verdict polling, fail-on-limit behavior and
  no starter auto-retry. A green starter only confirms that a job was accepted.
- Marketplace templates remove unused Logic App identities and use Blob Data
  Contributor rather than Owner for Function deployment storage. Runtime Storage
  still uses a connection string, so this is not a complete keyless design.
- Wizard fields no longer ask for unvalidated Function/Logic App names.
  Function/Storage names use uniqueString(resourceGroup().id); Logic App name is
  a fixed, RG-scoped default, not a uniqueString-generated name as the audit implies.
- Microsoft.Web 2025-05-01 is present in the official stable API specification.
- There are no nested Microsoft.Resources/deployments in these Marketplace
  templates. Partner Center automatic attribution is applicable per its guidance;
  the final generated Marketplace template still needs inspection before publishing.

OPEN RISKS / REQUIRED ACCEPTANCE GATES
R1. Recreated Function App identity in the SAME RG may break role deployment.
    The flattened role assignment GUID contains Storage ID, Function resource ID
    and role ID, but not principalId. Deleting/recreating the Function changes its
    system-assigned principal while keeping that GUID, causing the documented
    RoleAssignmentUpdateNotPermitted error if the old assignment remains.
    A normal update that preserves identity is different and need not fail.
    Retained the explicit fresh-RG testing scope. Do not use this package as a
    guarantee of destructive same-RG reinstall. Supporting that requires a design
    decision: restore principal-aware nested RBAC deployment and supply the real
    Marketplace tracking ID, or define/operator-test role cleanup. No role was
    deleted and no attribution ID was invented during this review.

R2. Role creation dependency is NOT proof of data-plane RBAC propagation.
    Test first onedeploy in a fresh RG, build/install dependencies, then repeat a
    normal update. If 403 occurs, capture deployment diagnostics. A fixed sleep
    alone does not guarantee propagation. Do not claim unattended installation
    reliability based only on ARM-TTK.

R3. TI permissions need confirmation before publishing.
    Wizard currently asks for Ti.Read.All, Ti.ReadWrite and Ti.ReadWrite.All.
    Follow-up verification: the ORIGINAL official ANY.RUN README at 9edc014
    lists exactly these same three Application permissions. They were NOT newly
    introduced by the Azure App 1.1.0 wizard. Our hardened README/installer is the
    version that narrowed the requirement to Ti.ReadWrite.
    Existing connector README/installer use Ti.ReadWrite; current Microsoft import
    API documentation lists Application Ti.ReadWrite.All. List API documentation
    distinguishes own-created indicators from all indicators. The code explicitly
    filters createdBy to the dedicated app, but the documentation/permission
    contract is inconsistent. Asked the user which app roles the working tenant
    actually grants. No speculative role removal or expansion was applied.
    Test application-only token + list + import + BatchDelete, and settle the
    documented minimum privilege set before release.

R4. API 429 retry contract for paid analysis must be confirmed with ANY.RUN.
    Current recovery clears submission intent on a definite 429 and may retry.
    No-duplicate guarantees depend on a rejected 429 not having created a task.
    Local tests cannot establish this external API guarantee.

R5. F5 remains: LeaseAlreadyPresent occurs before processing and consumes a queue
    delivery. It can exhaust dequeue attempts under repeated overlapping delivery.
    It was not reclassified as fixed. Avoid a casual catch-and-success change,
    which could acknowledge and lose a recoverable job.

R6. TI Feeds HTTP calls still use requests.request without an explicit timeout.
    A stalled upstream connection can occupy a run indefinitely until the host
    interrupts it; workflow concurrency=1 delays subsequent runs. This is existing
    baseline behavior, not introduced by 1.1.1. A separate bounded-request change
    with tests is recommended; no unrelated TI runtime change was made here.

R7. Live Sandbox tests must use an actual terminal ANY.RUN JSON report, verify
    the explicit completion signal accepted by the poller, check verdict/IOC
    enrichment, and restart mid-wait without creating a second paid task.
    Also test HTML HTTP rejection and interrupted/uncertain POST handling.

R8. Migration is not guaranteed to remove all stale indicators on the first run.
    Rejected import, empty feed or truncated feed intentionally prevents pruning.
    Use a dedicated app registration; another producer sharing clientId can be
    affected by createdBy-scoped synchronization. Verify repeated sync, unchanged
    IDs, and retention of unrelated/manual indicators in the tenant.

TESTING DOCUMENT QUALIFICATIONS
- Use new RGs as TESTING-1.1.0.md requests; upload only mainTemplate.json,
  createUiDefinition.json and artifacts/ from the revised package directories.
- Wizard links now intentionally use the TEST fork, not official main.
- Test loading/403/empty region responses as well as supported/unsupported regions.
- Never expose collected evidence or existing business data through the test
  artifact container. Prefer a separate test Storage account. Do not blindly
  toggle public access on the named shared account in the supplied testing document.
- The uploaded template must be invoked through its URL, or _artifactsLocation
  must be explicitly provided; local-file deployment has no templateLink.uri.
- Restart, wrong key and cleanup scenarios require operator authorization and
  should only affect the dedicated test resources. This review did not run them.
